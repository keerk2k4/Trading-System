# trading_ui

Angular 21 standalone-components workspace for the Sprint 9 Trading UI. This
README documents what actually exists in this folder today — what's built,
what's stubbed as an interim measure, and what Sprint 9 stories still need
real work — so a reviewer doesn't have to reverse-engineer the scope from the
diff.

## Scope of this delivery

Only four things were built here:

1. The Angular workspace skeleton (standalone components, no NgModules,
   Signals for state, functional providers).
2. The OpenAPI-Generator wiring (`openapitools.json` + `npm run generate:api`)
   that points at the two contracts under `../contracts/`.
3. Four working screens: **user registration**, **user login**, **admin
   login**, **user KYC submission**.
4. Unit tests for the above (Vitest, via `ng test`).

Everything else in the Sprint 9 ticket list — route guards, the order
ticket, the blotter, the full bearer-token interceptor, the full error
catalogue, and the Playwright E2E suite — is **not** built. See
"What's not done yet" below.

## Setting up

```bash
cd sprint09/trading_ui
npm install --legacy-peer-deps
```

**Why `--legacy-peer-deps`:** a plain `npm install` fails in this
environment with `Cannot read properties of null (reading 'edgesOut')`,
which is a bug in npm 10.9.7's arborist peer-dependency resolver when it
walks Angular 21's peer graph (tracked upstream as an `@npmcli/arborist`
issue, not something specific to this project). `--legacy-peer-deps` skips
the strict peer-resolution pass and installs cleanly. If your npm version
resolves the peer graph correctly, a plain install should also work — this
flag is a documented workaround, not a requirement of the dependency tree
itself.

## Running

```bash
npm start        # ng serve, http://localhost:4200
npm run build    # production build to dist/trading_ui
npm test         # unit tests (Vitest), single run: npm test -- --watch=false
```

## Workspace shape

```
src/app/
  core/
    config/
      api-config.ts            # base URLs for auth-service and trade-api (interim, see below)
    models/
      auth.models.ts           # interim hand-written TS interfaces mirroring contracts/auth-api.yaml
    services/
      session.service.ts       # signal-based, localStorage-backed access/refresh token store
      auth-api.service.ts      # register() / login() / adminLogin() HTTP calls
      kyc-api.service.ts       # submit() — attaches bearer token manually (interim, see below)
      error-message.util.ts    # maps a handful of known errorCode values to readable text (interim, see below)
  features/
    auth/
      register/                # user registration screen
      login/                   # user login screen
      admin-login/              # admin login screen
    kyc/
      kyc-form/                # KYC submission screen (no file upload — contract defines none)
  app.routes.ts                 # /, /register, /login, /admin/login, /kyc — all lazy-loaded, no guards yet
  app.config.ts                 # provideHttpClient(), provideRouter() — interceptor not registered yet
  app.ts / app.html / app.css   # root shell: nav bar, sign-out button when signed in
```

A new feature (e.g. the order ticket) belongs under `src/app/features/<area>/<screen>/`,
following the same pattern as `features/auth/*` and `features/kyc/*`: one folder per
screen with its own `.component.ts/.html/.css/.spec.ts`.

## Generating the typed API clients (not yet run here)

The Sprint 9 contract requires the two typed clients to be generated by
`openapi-generator-cli` from `../contracts/auth-api.yaml` and
`../contracts/trade-api.yaml` — never hand-written — and committed. That
generator is JVM-based and its jar is fetched from Maven Central
(`repo1.maven.org`) on first run. **This sandbox's network allowlist blocks
Maven Central**, so the generator could not actually be executed here, and
no generated client exists in this delivery.

The wiring is in place and ready to run in an environment with network
access to Maven Central and a JDK:

```bash
npm run generate:api        # both contracts
npm run generate:api:auth   # auth-api.yaml only
npm run generate:api:trade  # trade-api.yaml only
```

This writes to `src/app/generated/auth-api` and `src/app/generated/trade-api`.
Those paths are **deliberately not gitignored** — see the comment block at
the bottom of `.gitignore` — because the generated client is meant to be
committed and reviewed like any other source change.

### Interim stand-ins — delete these once real generation is run

Because generation could not run here, three files exist purely as
stand-ins so the four screens have something typed to call against. Each
carries a doc comment saying so, but to be explicit:

- `src/app/core/models/auth.models.ts` — hand-written interfaces mirroring
  `auth-api.yaml`. Replace all imports of this file with the generated
  models once `npm run generate:api:auth` has actually been run.
- `src/app/core/services/auth-api.service.ts` — hand-written HTTP calls.
  The generated client will supply an equivalent (and more complete)
  `AuthApi`/similar service; this file should be deleted and callers
  switched to the generated one.
- `src/app/core/services/kyc-api.service.ts` — same situation, for the KYC
  endpoint.

None of this is a substitute for the "Typed Clients Generated from the
Contracts" story — it only unblocks the four screens so they aren't stubbed
out entirely while that story is still open.

## What's not done yet

Being explicit about this so nothing here is mistaken for finished work.
Referencing the Sprint 9 ticket names:

- **Typed Clients Generated from the Contracts** — not run (blocked by
  sandbox network access to Maven Central, see above). The interim
  hand-written stand-ins above need to be deleted once this is run for
  real.
- **The Bearer Token Interceptor** (one interceptor, allow-list by origin)
  — not built. `kyc-api.service.ts` attaches the bearer token by hand as a
  stopgap; that logic needs to move into a real `HttpInterceptorFn`
  registered in `app.config.ts` and applied to every outgoing request that
  targets an allow-listed origin, not just this one call site.
- **Route Guards and the Return Address** — not built. `app.routes.ts` has
  no guard on `/kyc`; anyone can navigate there directly whether or not
  they're signed in (the component itself checks `session.isSignedIn()`
  before submitting, but that's not the same as a route guard redirecting
  with a return address).
- **Order Ticket with Client-Side Validation** — not built. No route,
  component, or service for order placement exists.
- **Blotter with Status Badges and the NEW Path** — not built.
- **Render Every Code in the Error Catalogues** — only partially covered.
  `error-message.util.ts` maps `AUTH-401, AUTH-403, AUTH-409, VAL-422,
  KYC-409, KYC-404`, plus the status-0 and unrecognized-code fallbacks. It
  does not cover the trade-api error codes (`ACC-404, ACC-403, INS-404,
  ORD-400, ORD-409`) since no trade-facing screen exists yet to surface
  them.
- **Playwright: Sign In and Place an Order** — not built. No Playwright
  config, no e2e directory, none of the `E2E_*` environment variables are
  wired up.
- **Secret-Free Production Bundle** — the production build was checked
  against the three forbidden patterns (`x-api-key`/`api-key`,
  `fauxnance`, `execute-api.*.amazonaws.com`, `jwt_secret`) via
  `grep -riE` over `dist/trading_ui` and came back clean, but
  `api-config.ts` still hardcodes `localhost` URLs as a placeholder — that
  needs to become environment-driven before this can be called done for
  real deployment targets.
- **OpenAPI Served by the Running Service** — this is an auth-service
  (backend) story, not a UI story; it's listed in the Sprint 9 ticket dump
  but belongs to `sprint09/auth-service`, not `trading_ui`. Flagging this
  so it isn't mistakenly tracked as UI work.

## Other notes

- `npm audit` reports 9 vulnerabilities (2 low, 1 moderate, 6 high) after
  adding `@openapitools/openapi-generator-cli` as a dev dependency. It's a
  dev-only, build-time tool (not shipped in the production bundle), but
  worth running `npm audit` yourself and deciding whether to pin different
  versions before this goes further.
